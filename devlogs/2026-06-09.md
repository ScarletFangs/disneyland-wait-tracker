# Devlog — 2026-06-09

## Project

Disneyland Wait Tracker — Building the API service and completing the data layer

## Progress

- Added the HTTP package and wrote the API service that fetches live Disneyland ride and show data from the ThemeParks.wiki API.
- Refactored two separate fetch methods into a shared helper so the API only gets called once instead of twice for the same data.
- Wired up the land-name lookup so each ride gets its land joined from a local JSON map, since the API does not include that info.
- Updated both data models to accept an optional land parameter and confirmed everything works by printing real ride names, wait times, and lands to the console.
- Registered the ride lands JSON file as a Flutter asset and updated the progress tracker to reflect Phase 2 complete.

## Reflection

This session was a follow through on last session's goals and I ended up going further than planned. I originally just wanted to get `fetchRides()` printing to the console but I also wrote `fetchShows()` and the land join because the patterns were similar and I wanted all the data fetching done before moving on. The method chaining with `.where().map().toList()` felt better this time around. I am more comfortable writing the arguments inside each function but I still do not have full intuition for which methods to chain and in what order. I hit two runtime errors this session. One was a type mismatch where dart did not know a list of dynamic was actually a list of rides and the other was a stack overflow from accidentally calling `toString()` on itself. I had the right instinct for what was going wrong in both cases but I needed the explanation to put it into words. I am still doing hint based coaching where I write all the code myself and the AI asks me questions to guide my thinking. I pushed past the original scope because it made sense to finish the data layer as a unit rather than leaving half of it for next time.
