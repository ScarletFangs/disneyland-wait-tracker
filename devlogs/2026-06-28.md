# Devlog — 2026-06-28

## Project

Disneyland Wait Tracker — Modeling Lightning Lane and building the Ride Detail screen

## Progress

- Modeled Lightning Lane after checking the live api directly, where I found it returns one of two return time types and never both, and used the presence of a price to tell the paid single pass apart from the included multi pass return.
- Built the Ride Detail screen that opens from a tap on the dashboard, carries the tapped ride across, and shows the status, wait, and Lightning Lane info with empty states for when it is not available or finished.
- Added a favorite star that reads from Firestore when the screen opens so it shows the right state, and writes to Firestore on tap with an optimistic flip.
- Hardened the favorite toggle with a try catch that reverts the star if the write fails, after realizing the screen could close before the response comes back.
- Worked through the null safety wall again by checking for null and letting the type promote, instead of forcing it with the bang operator.

## Reflection

This session started with the lightning lane model. I know from going to disneyland that there are different types of lightning lanes, so before I assumed anything I wanted to find out how that information is represented in the api, if at all. Checking the live data showed it returns one of two return time keys and never both. I modeled it as a single object where the presence of a price tells me which type it is. The null safety came up again when the user id came back as a string that could be null. It is clearer this time but it is still not baked into me to check for it on my own when the situation calls for it. The favorite star was the first screen that both reads from and writes to firestore. My first version was simple because I did not think about the case where the widget closes or changes before a response comes back. I changed it to a try catch that reverts the star if the write fails. The navigation and passing the ride into the screen made sense to me, but the statefulwidget splitting into two classes is something I still need to work with more to fully understand.
